# Architecture

This document describes the architecture currently accepted for implementation. Module-specific details must only be added after the corresponding code exists.

## System shape

```text
Flutter presentation
        |
        | typed in-process bridge
        v
Rust application/core API
        |
        +--> music domain
        +--> provider API
        +--> QQMusicProvider
                  |
                  v
            QQMusicClient
                  |
                  v
              QQ Music
```

There is no runtime HTTP sidecar between Flutter and the Rust core.

There is currently no independent Provider Registry. Bootstrap composes the concrete `QQMusicProvider` through provider contracts; a registry should exist only after a real multi-provider selection or discovery requirement appears.

## Dependency direction

- Presentation depends on generated or explicit bridge types, never raw QQ Music response models.
- The bridge adapts calls and data ownership. It does not contain product business rules.
- Provider implementations depend on provider interfaces and project domain models.
- `QQMusicProvider` maps raw protocol results from `QQMusicClient` into stable project domain models.
- `QQMusicClient` owns transport, request construction, cookies, session details, signing/QIMEI when required, and raw protocol models. It does not know Flutter.

## Current modules

- `apps/flutter` contains a centralized official-Flutter light/dark Material theme with a small set of presentation tokens; adaptive Material 3 authentication; QQ Music Track/Artist/Album/Playlist search; Album Tracks and canonical metadata; Artist Tracks/Albums and multi-Artist selection; public recommended playlists; authenticated Radar Tracks and favorite Album/Artist collections; regional new-Album releases; typed new-song channels; grouped current rankings and paged ranking Tracks; complete user-playlist collection; paged playlist-detail with retained Album context navigation; foreground playback/queue with current-Track Album/Artist navigation; an adaptive immersive artwork/lyrics now-playing page; synchronized-lyric surfaces; read-only Track comments; and one bounded Track-associated MV surface. Search and Discover share a presentation-only secondary selector that uses one explicit menu below 680 px and visible segmented controls at wider widths while keeping every typed controller independent and retained. All four Search types and five Discover sections share bounded loading/content-state presentation while their copy, actions, typed failures, contextual selectors, controllers, and live-region decisions remain page-owned. Album, Artist Tracks, Ranking, Radar, and New songs share one compact/desktop Material Track tile over the existing presentation-safe Track summary; its optional context menu forwards only validated Album/Artist values into existing retained routes, while contextual Playlist and Search rows remain separate. The core catalog pages share an adaptive artwork/page-type/title frame plus loading/message presentation while page-specific metadata, actions, typed failures, copy, retry rules, controllers, and live-region decisions remain page-owned. Flutter owns short-lived Dart controllers/gateway adapters, shared presentation-safe Album/Artist summary types, one shared serialized platform-vault boundary, a plugin-independent foreground-audio port/controller plus its selected plugin adapter, a separate disposable MV-only engine adapter, and Dart integration/widget tests.
- `crates/music-domain` contains provider-independent provider/playlist/track/Album/Artist/ranking/comment/MV identities, summaries and bounded Track/Artist/Album/Playlist-search/catalog/recommendation/ranking/library/comment/MV values, including optional Album context and validated credited Artists on Track summaries, canonical Album details, favorite-Album and favorite-Artist pages, page-numbered Radar Tracks, typed regional new-Album releases, typed whole-response new-song collections, separate hot/newest read-only Track comments, and a bounded Track-associated MV plus secret-bearing source; a redacted short-lived resolved-media source; deterministic positional playback queue; and synchronized line/word lyric timing. Provider-owned identity values remain opaque outside their implementation.
- `crates/provider-api` contains the UI-free provider descriptor/capabilities plus provider-neutral Track/Artist/Album/Playlist search, Album Tracks/details, Artist Tracks/Albums, recommended playlists, authenticated Radar Tracks and favorite Album/Artist pages, regional new-Album releases, whole-response new-song channels, current ranking groups/Tracks, read-only Track comments, Track-associated MV, QR authentication, owned/complete user-playlist, paged playlist-detail, standard-media-resolution, and synchronized-lyrics contracts.
- `crates/qqmusic-client` owns the raw QQ Music client boundary. It contains redacted credential/restore models, versioned secure-storage serialization, a Rustls-backed bounded HTTP implementation, direct paged Track/Artist/Album/Playlist search, Album-song and canonical-detail loading, Artist-song and Artist-album loading, public recommended-playlist loading, authenticated Radar Track and favorite Album/Artist loading, regional new-Album and typed new-song loading, current ranking list/detail loading, anonymous legacy Track-comment loading, exact Track-detail-to-associated-MV metadata/source loading, cross-validated WeChat QR flows, credential verification plus bounded optional account identity, owned/favorite playlist fetching, ordinary/liked-songs detail-page fetching, media dispatch/vkey resolution, bounded cloud-QRC decryption/parsing, and cancellable lifecycle coordinators.
- `crates/provider-qqmusic` retains credential state; maps raw search, Album, Artist, recommendation, ranking, comment, MV, authentication, playlist, track, media, and lyric protocol values into provider/domain contracts; aggregates bounded owned/favorite pages; routes ordinary, public catalog, and built-in liked detail pages; and truthfully advertises `Search`, `Catalog`, `Recommendations`, `Authentication`, `UserLibrary`, `Lyrics`, `Comments`, `MusicVideo`, and `MediaResolution`.
- `bridges/flutter` adapts core/provider status, Track/Artist/Album/Playlist search, Album Tracks/details, Artist Tracks/Albums, recommended playlists, authenticated Radar Tracks and favorite Album/Artist pages, regional new-Album releases, typed new-song collections, current ranking groups/Tracks, read-only Track comments, Track-associated MV, authentication, signed-in account summary, credential persistence, complete user-playlist loading, one playlist-track page, one standard-media resolution, synchronized lyrics, and one Dart-owned positional playback queue into presentation-safe generated types. Secret-bearing credential and media handoffs stay narrow and short-lived rather than becoming presentation models.

The current concrete bootstrap flow is:

```text
Flutter main
  -> RustLib.init
  -> bridge bootstrap_status
  -> QqMusicProvider descriptor
  -> typed BootstrapStatus
  -> Flutter bootstrap page
```

The raw authentication flow reaches a validated credential inside the core:

```text
QQMusicClient
  -> WeChat QR connect page
  -> bounded UUID parsing
  -> QR image fetch and signature validation
  -> transient unconfirmed QR session
  -> one bounded long-poll
  -> protocol state or internal redacted authorization code
  -> named musicu Login RPC
  -> validated redacted Credential
```

Request/response diagnostics omit query values, headers, bodies, QR identifiers, image bytes, authorization codes, credential keys, and refresh material. The one-shot client remains independent of UI state. A separate login coordinator owns attempt generations: starting again supersedes the old generation, cancellation/disposal drops in-flight create/poll/exchange futures, and a credential is accepted only while its generation is current. Authorization codes never need to leave that coordinator. One monotonic 180-second deadline spans QR creation, polling, and exchange; it drops blocked requests. Three consecutive transport failures are caller-retryable, the fourth finishes the session, and any reached protocol response resets the count. The coordinator does not hide polling or retry loops. Default protocol tests use synthetic sanitized responses; live tests are separate, ignored, and explicitly environment-gated.

The typed authentication boundary is:

```text
Flutter
  -> start WeChat QR login
  -> Rust-opaque session handle + image bytes/media type
  -> explicit advance/cancel calls
  -> Provider-neutral progress or failure enum
  -> coarse authentication and persistence state

Rust opaque session
  -> QQMusicProvider QR session
  -> WechatQrLoginCoordinator
  -> Credential retained inside QQMusicProvider
```

The opaque handle exposes no fields and carries generation-specific cancellation authority, so cancelling an old Dart object cannot cancel its replacement. Concurrent `advance` calls fail explicitly instead of creating a hidden polling queue.

After successful authentication, credential persistence follows a separate narrow path:

```text
QQMusicProvider credential
  -> Rust versioned serialization and invariant checks
  -> dedicated Bridge export of short-lived opaque bytes
  -> Dart platform-vault adapter (Base64 transport envelope only)
  -> flutter_secure_storage
  -> native platform secure storage
```

The controller sees only stored/unavailable status. It cannot inspect credential fields. The mutable bridge buffer is zeroed after the asynchronous write. Secure write alone does not satisfy credential restore.

Startup now performs the reverse narrow handoff before constructing the login controller:

```text
native platform secure storage
  -> Dart vault read and Base64 decode
  -> dedicated Bridge import of optional opaque bytes
  -> Rust version/invariant validation and local expiry plan
  -> signed out | verification required | locally expired | typed failure
  -> exact verification attempt ID
  -> QQMusicProvider -> QQMusicClient user-info verification
  -> authenticated | rejected | retryable/typed failure
```

The loaded Dart byte buffer is zeroed after the synchronous Rust import. Rust retains verification and locally expired candidates in distinct internal states, and neither makes `has_authenticated_credential` true. The Provider promotes a candidate only when QQ Music returns zero global and named-result codes. Independently observed rejection codes clear in-memory state; transport, service, other upstream, and malformed-response failures retain the candidate for explicit retry. Malformed, unsupported, and platform-access failures remain distinct and are never auto-deleted. The Dart platform edge deletes secure storage only after an explicit rejection and reports cleanup failure separately. Authentication and library gateways share one serialized vault queue, so an old rejection cleanup cannot remove a newer QR credential.

Restore-verification attempt IDs are process-local cancellation authority, not QQ Music identifiers. The Provider checks both the exact attempt and candidate before and after network work. Starting a new QR login clears that authority, so a late verification cannot overwrite the replacement session. Dart additionally uses controller generations to suppress late presentation updates after retry, QR replacement, cancellation, or disposal.

The signed-in account-summary capability reuses the same bounded `GetLoginUserInfo` request without changing credential-validity semantics. `QQMusicClient` optionally maps only nested `info.nick` and `info.logo`; a valid response with no usable profile remains valid for restoration. `QQMusicProvider` separately requires a bounded display name for `AccountSummary`, rechecks the exact credential after the await, and clears state only for the already-evidenced rejection codes. A single-use cancellable Bridge handle exposes only display name, optional avatar URI, and coarse failures. The Dart gateway rejects contradictory DTO shapes and serializes secure-vault cleanup after explicit rejection. Account ID, cookies, keys, raw profile response, membership/social fields, and presentation state do not cross the boundary; page integration remains deferred while visual UI work is frozen.

Authentication presentation keeps asynchronous status/error information separate from controls. Active QR waiting, scanned-awaiting-confirmation, and reconnecting copy plus saved-session or QR terminal copy expose only their existing title and explanation as one semantic live region; the QR image, cancel, retry, cleanup, and replacement-code controls remain independent semantic nodes. This is presentation behavior only and does not change credential classification, polling, retry authority, or protocol state.

Explicit sign-out is local and ordered across the same boundary; it does not invent a remote QQ Music account-logout protocol. `QQMusicProvider` cancels the current QR generation, clears restoration-verification authority, and replaces authenticated, pending, or expired credential state with signed out under the existing lock order. Late verification or Provider work therefore resolves as replaced instead of reviving the session. The synchronous Bridge reports only whether Core performed that transition. Dart deletes the one serialized platform-vault entry only after Core succeeds: Core failure retains both current login and vault, while vault failure leaves Core signed out, reports that restart may restore the saved copy, and offers cleanup retry. `LoginController` owns one in-flight sign-out Future, so repeated activation cannot duplicate Core/vault work; retry presentation stays visible and disabled while that operation runs, and an unexpected gateway exception is reduced to the same Core-unavailable state. The authenticated page confirms the action and stops foreground playback while vault deletion is pending.

QR creation has a separate opaque start-attempt number reserved by the Bridge adapter before network work begins. Cancel/restart/dispose can cancel that exact pending creation; comparison against the current start attempt prevents a late old controller from cancelling its replacement. After a challenge returns, the Dart controller discards that start operation and uses the Rust-owned session handle. Dart owns presentation stages, one-second network-reconnect delay, adaptive layout, animation, and late-result visibility guards. Rust remains the authority for protocol deadlines, failure counts, session generations, and credential state.

## Flutter / Rust boundary

Place logic in Rust when it would remain useful if Flutter were replaced by another UI toolkit. Keep logic in Dart when it exists primarily to present or interact with the current UI.

The bridge must not synchronize hover, focus, animation progress, navigation rail state, or dialog visibility. It may expose coarse application operations, opaque operation handles, and serializable domain results. Opaque handles must not expose raw provider session identifiers or secret material.

The current bridge is generated by `flutter_rust_bridge` 2.13.0. Linux x64 builds its bridge crate directly with system Cargo because the generated Cargokit backend requires rustup. On Linux hosts without rustup, Android uses a second localized system-Cargo Gradle task for one explicitly requested ARM64 or x64 target: the matching distribution `rust-src` builds `std`, NDK API 24 supplies the linker, and the resulting library is merged into the plugin AAR before native-library packaging. ARM64 additionally links the NDK compiler-runtime archive and fails if an unresolved `__aarch64_*` symbol survives. The application maps Flutter's explicit target platform into Gradle ABI filters so transitive JNI libraries cannot advertise an incomplete ABI. ARM64 release artifact inspection plus translated AVD startup and native x64 emulator FFI have passed; physical ARM64, other hosts, and other ABI sets retain unvalidated paths. These exceptions are tracked as TD-001.

## Provider architecture

Providers expose data plus explicit capabilities such as authentication, catalog, recommendations, user library, lyrics, comments, and media resolution. A provider can implement only a subset. The first implementation is QQ Music; capability interfaces must remain small enough to reflect proven behavior.

Provider code never returns Flutter widgets or presentation-specific models.

The first catalog capability is provider-neutral paged Track search. `QQMusicClient` sends one bounded anonymous `music.search.SearchCgiService/DoSearchForQQMusicDesktop` request directly to QQ Music, validates global/module codes, exact requested-page metadata, continuation, total, and the minimum Track/artist/album identity and display fields, and caps query, page size, response bytes, and timeout. Its request and response diagnostics retain neither query nor result content. `QQMusicProvider` maps these raw summaries into the same opaque provider-scoped `TrackSummary` consumed by playlist playback and does not consult or mutate credential state; raw QQ response models stop at the client boundary.

The Bridge exposes one single-use `QqMusicTrackSearchPageLoadHandle` with typed page/failure output and exact run/cancel/isActive lifecycle. The opaque handle redacts its retained query, and cancellation drops the losing Provider/network future. Flutter owns a short-lived query controller with first-page loading, empty, retryable error, pagination, append failure, replacement cancellation, stale-generation suppression, clear, and disposal states. The authenticated Library surface opens Search as a local adaptive page, preserves the existing queue/playback owner, and restores focus to the Search entry on return. Selecting a result replaces and starts the existing Rust-backed queue; adding a result delegates one push without parsing its opaque identity.

Direct Artist Search is a separate provider-neutral paged capability rather than a mixed raw-result union. `QQMusicClient` sends the exact Desktop type-1 request under the named `music.search.SearchCgiService` key, validates current/next page, total, requested page size, and the positive numeric-ID/MID/name identity needed by existing Artist routes, and retains neither query nor Artist content in diagnostics. `QQMusicProvider` maps those rows into existing opaque `ArtistSummary` values without consulting credential state; the Bridge exposes an independent single-use cancellable Artist-search handle. Flutter presents Artists as one option in the typed Search control, keeps an independent query/result/pagination/cancellation generation for it, and opens the existing Artist Tracks/Albums page without reloading Search on return. MV/user Search, mixed-result ranking, suggestions, history, and hot words remain absent.

Direct Album Search follows the same typed separation without turning Search into a heterogeneous union. `QQMusicClient` sends the exact Desktop type-2 named-key request, validates exact page size/current/next/total metadata plus positive numeric-ID/MID/title identity, and ignores volatile tracing and optional display metadata. `QQMusicProvider` maps rows into existing opaque `AlbumSummary` values and the Bridge exposes an independent single-use cancellable Album-search handle. Flutter maintains an independent Album controller and generation, passes Album results to the existing Album Tracks page, and preserves that state on return. MV/user Search, mixed-result ranking, suggestions, history, hot words, and Album metadata expansion remain absent.

Direct Playlist Search is another separate provider-neutral page rather than a mixed raw-result union. `QQMusicClient` sends the exact Desktop type-3 named-key request, validates exact page/current/total metadata, server `nextpage`, positive numeric-string playlist identity, nonblank title, and Track count, and keeps query and returned content out of diagnostics. It accepts a short nonterminal page because bounded service evidence returned four rows for a five-row request while still advertising continuation. `QQMusicProvider` maps rows into existing opaque `catalog:<id>` playlist summaries without consulting account state, and the Bridge exposes an independent single-use cancellable Playlist-search handle. Flutter maintains the fourth independent query/result/pagination/cancellation generation, keeps the compact selector horizontally reachable, passes results to the existing public playlist-detail/queue path, and preserves all four Search states on return. Mixed results, creator profiles, suggestions/history/hot words, mutation, and generic Search/navigation infrastructure remain absent.

Search items may carry an optional provider-neutral `AlbumSummary`; results lacking a validated provider-owned Album identity simply expose no Album action. `QQMusicClient` sends one bounded anonymous `music.musichallAlbum.AlbumSongList/GetAlbumSongList` request, validates the exact Album MID and returned offset/total/continuation, and maps only the same minimum Track shape used by playback. `QQMusicProvider` alone encodes and parses opaque Album identity and implements the small `AlbumTracksProvider` catalog contract. The Bridge exposes a separate single-use cancellable Album-page handle. Flutter owns initial/empty/error/retry/pagination/append-failure state and keeps each parent page mounted behind the shared local Album page so its state survives return. Favorites/mutation, mixed-result Search, and a generic catalog runtime remain absent.

Canonical Album metadata is a separate `AlbumDetailsProvider` capability rather than a prerequisite or extension of the Track page. `QQMusicClient` sends one bounded anonymous `music.musichallAlbum.AlbumInfoServer/GetAlbumDetail` request using the existing safe MID as `albumMId`, validates global/module/data groups, exact returned MID, positive Album and credited-Artist identity, canonical title, 4 KiB short fields, and a separate 128 KiB description bound, and ignores booklet/wiki/video/rights/tracking fields. `QQMusicProvider` maps it into `AlbumDetails`; the Bridge exposes an independent single-use cancellable handle with content-redacted diagnostics. Flutter owns a second short-lived controller beside Album Tracks, so metadata loading/failure/retry/cancel/stale/disposal never hides loaded Tracks or queue actions. Canonical title, credits, release/type/genre/language/company render adaptively, while full description is reachable through a compact bottom sheet or desktop dialog. Only successfully loaded validated credits become actions: one Artist opens directly and collaborations require bounded explicit selection. Album mutation, pre-detail Artist actions, cache, and generic detail/navigation infrastructure remain absent.

Search items also carry every credited Artist that has a validated provider-owned numeric ID, MID, and display name; invalid identities expose no Artist transition instead of inventing one. `QQMusicClient` sends one bounded anonymous `music.musichallSong.SongListInter/GetSingerSongList` request using the independently evidenced numeric-ID/`num` shape, validates the requested Artist MID, exact offset, total, continuation, page bound, and minimum Track shape, and retains no content in diagnostics. `QQMusicProvider` alone encodes and parses opaque Artist identity and implements the small `ArtistTracksProvider` catalog contract. The Bridge exposes a separate single-use cancellable Artist-page handle. Flutter owns multi-Artist selection plus initial/empty/error/retry/pagination/append-failure/cancel/stale/disposal state and keeps Search mounted while an Artist page is open.

The same opaque Artist identity now drives a separate provider-neutral `ArtistAlbumsProvider` contract. `QQMusicClient` sends one bounded anonymous `music.musichallAlbum.AlbumListServer/GetAlbumList` request and validates exact Artist MID, offset, total, continuation, page bound, Album numeric/MID identity, and title. The request deliberately uses `num`: bounded real-service comparison showed the conflicting `number` field was ignored and returned the default 30 rows. `QQMusicProvider` maps validated rows into the existing `AlbumSummary`, and the Bridge exposes a single-use cancellable Artist-Album page handle rather than widening Artist Tracks. Flutter loads Albums lazily, preserves Track and Album section state, adapts between compact list and desktop grid, and nests the existing Album page so back returns Album → Artist → Search. Biography, Artist artwork/details/follows, discography filters, similar Artists, MV, and a generic catalog runtime remain absent.

The first recommendation capability is a provider-neutral offset-paged public-playlist page. `QQMusicClient` sends one bounded anonymous `music.playlist.PlaylistSquare/GetRecommendFeed` request with `From` and `Size`, validates global/module codes, the nested `List[*].Playlist.basic` identity/title plus optional artwork/count, exact page bounds, continuation, response bytes, and timeout, and retains neither returned content nor identifiers in diagnostics. Pagination advances by the raw returned row count: bounded anonymous probes showed that `FromLimit` remains a feed bound rather than a next-page cursor. `QQMusicProvider` maps rows to `PlaylistSummary` with opaque `catalog:<id>` identities and implements the small `RecommendedPlaylistsProvider` contract without consulting account state; authenticated playlist detail later parses that identity and reuses the existing ordinary-detail operation. The Bridge exposes one single-use cancellable recommendation-page handle. Flutter owns initial/empty/error/retry/pagination/append-failure/cancel/stale/disposal state, renders an adaptive discovery surface, and keeps it mounted while existing playlist detail is open. Heterogeneous recommendation feeds, personalization, radio, mutation, and a generic recommendation runtime remain absent.

Authenticated Radar recommendations use a second small recommendation contract rather than widening the public playlist page into a mixed feed. `QQMusicClient` sends credential-bearing `music.recommend.TrackRelationServer/GetRadarSong` requests with service-owned `Page`, validates global/module/rejection codes, `VecSongs[*].Track`, `HasMore`, minimum playback Track shape, response bounds, and safe identifiers, and redacts credentials plus returned content. `QQMusicProvider` rechecks the exact authenticated credential after the await, clears it only on explicit rejection, rejects a late result after account replacement, and maps the raw page into existing provider-neutral `TrackSummary` values. The Bridge exposes one single-use cancellable Radar-page handle with coarse authentication and transport failures. Flutter loads Radar lazily as a third retained Discover state, pages by `Page`/`HasMore`, deduplicates exact provider/opaque identity across the observed overlap, uses the shared serialized vault for explicit rejection cleanup, and delegates play/add actions to the existing Rust-backed queue. Anonymous structural probes do not establish personalization or recommendation quality; endless autoplay, feedback, daily aggregation, heterogeneous Home shelves, and a generic recommendation runtime remain absent.

Regional new-Album releases use a separate provider-neutral Catalog contract rather than widening the heterogeneous Home or recommendation surfaces. `QQMusicClient` sends one bounded anonymous `newalbum.NewAlbumServer/get_new_album_info` request with an exact QQ-owned area, zero-based `start`, and `num`; validates global/module codes, numeric total, page bounds, Album numeric/MID/title identity, nested credited Artist identity, optional nonblank release date, response bytes, and timeout; and retains no returned content in diagnostics. `QQMusicProvider` alone maps the six project regions to numeric QQ areas and maps the result into existing opaque `AlbumSummary` and `ArtistSummary` values. The Bridge exposes one single-use cancellable page handle. Flutter loads New Albums lazily as a fourth retained Discover state, owns region replacement plus initial/empty/error/retry/pagination/append-failure/cancel/stale/disposal behavior, advances by raw rows before deduplication, and opens the existing Album/queue path. Editorial/tracking cards, notifications, cache refresh, Album mutation/detail expansion, and a generic catalog runtime remain absent.

Typed new-song channels use another small provider-neutral Catalog contract rather than widening Discover into a heterogeneous Home feed. `QQMusicClient` sends one bounded anonymous `newsong.NewSongServer/get_new_song_info` request for one of six QQ-owned categories, validates global/module codes, exact returned category, a maximum 200-row whole response, minimum Track/Artist identity and title, response bytes, and timeout, and retains no returned content in diagnostics. Because the operation has no pagination input, Domain and Bridge expose no invented cursor. `QQMusicProvider` maps the raw Tracks through the shared Track mapper, preserving optional Album and every validated credited Artist. The Bridge exposes one single-use cancellable collection handle. Flutter loads New Songs lazily as a fifth retained Discover state, owns first/empty/error/retry/category-replacement/cancel/stale/disposal behavior, keeps every category horizontally reachable on compact screens, and delegates play/add actions to the existing queue. Editorial tags, heterogeneous shelves, personalization claims, infinite radio/autoplay, caching, and a generic recommendation runtime remain absent.

Current rankings use a separate provider-neutral `RankingsProvider` contract rather than widening recommendations into heterogeneous content. `QQMusicClient` sends bounded anonymous `music.musicToplist.Toplist/GetAll` and `GetDetail` named-key requests without account state, validates group and ranking identity, optional period/artwork, current-detail identity, total, page bounds, and the same minimum Track shape used by playback, and retains no editorial content in diagnostics. `QQMusicProvider` alone turns numeric `topId` into opaque `ranking:<id>` identity and maps detail Tracks into existing Domain summaries. The Bridge exposes separate single-use cancellable group and Track-page handles. Flutter keeps Playlists and Rankings as independent retained states inside Discover, owns ranking pagination/retry/cancel/stale/disposal behavior, and sends selected Tracks to the existing Rust-backed queue. A ranking identity always selects QQ Music's current service period; history selection, subscriptions, third-party charts, mixed Home shelves, and a generic catalog runtime remain absent.

The first user-library operation loads authenticated account-owned playlists via `QQMusicClient` `PlaylistBaseRead/GetPlaylistByUin`. QQ-specific, diagnostics-redacted protocol summaries preserve both playlist and directory identifiers. `QQMusicProvider` maps them into provider-independent `PlaylistSummary` values whose `PlaylistId` contains a stable provider ID and an opaque provider-owned value; generic domain and Flutter code cannot parse QQ identity rules. The narrow `OwnedPlaylistsProvider` remains available for the created-only collection.

`QQMusicClient` also implements one bounded page of `PlaylistFavRead/CgiGetPlaylistFavInfo`. It requires the credential's encrypted UIN, constrains page size to 100, and returns typed pagination plus protocol summaries without performing hidden loops. `QQMusicProvider` implements the complete `UserPlaylistsProvider` contract by loading owned rows first, following at most ten favorite pages, advancing offsets by raw page length, rejecting empty continuing pages, and deduplicating by QQ playlist ID. Owned identities remain `owned:<tid>:<dirId>` and favorite identities become `favorite:<id>` inside provider-owned opaque values. Every network await rechecks the exact credential; only explicit rejection for the current credential signs out. The hard safety limit is TD-005.

The Bridge exposes the complete Provider operation through a single-use `QqMusicUserPlaylistLoadHandle`. `run`, exact `cancel`, and `isActive` are the only operations; cancellation drops the losing Provider/network future, including an in-progress favorite page, and concurrent runs fail explicitly. Generated Dart receives provider ID, opaque playlist ID, title, optional artwork/count, and a coarse failure enum. Credential, QQ dual IDs, pagination, and merging rules remain outside Flutter.

The Library's Playlists section presents the combined Provider result through an adaptive page-owned controller. Its loading/retry/empty/error presentation cancels replaced operations and suppresses late results after restart or disposal. An explicit refresh preserves the last complete content or empty snapshot while work is active and after retryable failure; a complete success replaces it, while authentication/replacement/rejection still clears private rows. This is presentation-local snapshot state and does not cache Provider responses outside the authenticated page lifetime. Retryable transport/service/structural/Core failures do not offer a sign-in reset for the credential they explicitly retain; account-state failures do. An asynchronous full-screen failure announces only its title/explanation as one live region, leaving recovery controls as independent semantic actions. Desktop uses a bounded artwork grid; narrow layouts use a touch-sized list. Structural or safety-limit failures show no partial new list. Rows open local playlist-detail presentation without parsing source-specific opaque IDs.

Favorite Albums are a separate paged `FavoriteAlbumsProvider` library capability rather than another playlist kind or a generic library union. `QQMusicClient` calls the authenticated legacy `fav/fcgi-bin/fcg_get_profile_order_asset.fcg` route directly with `reqtype=2`, exact account identity, credential Cookie, and inclusive `sin`/`ein`; it validates a one-mebibyte response, global/subcodes, boolean-or-0/1 continuation, exact total/page consistency, both observed Album field casings, and minimum positive ID/safe MID/nonblank title. Only the directly evidenced global code `4000` is credential rejection; every other nonzero code remains a retryable upstream failure and cannot clear login state. `QQMusicProvider` rechecks the exact credential after the await and maps the page into existing opaque `AlbumSummary` values. A single-use cancellable Bridge handle exposes only offset/total/continuation, Album summaries, and coarse failures. Flutter owns first/empty/error/retry/append/cancel/stale/disposal state, uses the shared labeled Material loading/content-state panels without merging typed recovery rules, clears private rows on account replacement/rejection, serializes rejection cleanup through the shared vault, and adapts between compact list and desktop grid. The page initializes lazily on the first Albums-section visit, then remains mounted across Library-section and width changes and while the existing Album Tracks/details/queue page is open. Favorite mutation, cache/automatic refresh, and a generic library or navigation framework remain absent.

Favorite Artists are a separate paged `FavoriteArtistsProvider` capability using the authenticated `music.concern.RelationList/GetFollowSingerList` operation with encrypted `HostUin`, raw-row offset `From`, and bounded `Size`. `QQMusicClient` validates global/module codes, the required `Total`/`HasMore`/`List` shape, exact pagination consistency, safe Artist MID, nonblank name, one-mebibyte response, and timeout. `QQMusicProvider` applies the same exact credential-candidate/rejection/replacement rules as other authenticated pages and maps rows into honest MID-only `artist:-:<mid>` identities. Existing Artist Track and Album routes accept that identity: the Track client sends the already-evidenced MID request rather than fabricating a numeric Artist ID. The single-use cancellable Bridge carries only provider-neutral Artist summaries and coarse failures. Flutter owns collection lifecycle and shared-vault rejection cleanup, uses the same labeled initial-state panels as Favorite Albums while retaining page-owned copy/actions, switches between compact list and desktop grid, and retains collection → Artist → Album state around the existing queue. The Artist root initializes lazily on first visit and then remains mounted independently across section and width changes. Follow mutation, biography/social fields, automatic refresh/cache, stored-account probes, and generic library/navigation infrastructure remain absent.

The protocol client has separate bounded operations for ordinary playlist pages (`disstid`) and the built-in liked-songs directory (`dirid: 201` plus encrypted UIN). Both return QQ-specific track, artist, and album summaries with typed pagination and failures. `QQMusicProvider` alone parses playlist opaque identities, selects the request route, and maps the result into a provider-neutral `PlaylistTracksPage`. Its shared Track mapper preserves an optional validated `AlbumSummary` and every validated credited `ArtistSummary` from the already-present protocol values; all current QQ Track-producing surfaces therefore receive the same context without reparsing identity or guessing from names. Track IDs remain provider-scoped opaque values containing the QQ fields needed by media and lyrics; generic Domain and presentation code cannot interpret them. The page boundary is intentional: playlist detail does not hide an unbounded full-list loop. The Provider rejects a continuing empty page and rechecks the exact authenticated credential after the network await. Flutter opens a selected playlist locally from the library surface and creates a short-lived paged controller. Because this detail is presentation-local rather than a Navigator route, the authenticated page consumes one platform back request, desktop `Alt+Left`, or Browser Back while detail is selected and returns to its existing library controller. The same page-level return path sends a primary Discover, Search, or Library peer back to Home; Home itself leaves platform back unblocked. Its non-traversable fallback focus lives below the existing playback shortcut scope, so a locally opened overlay remains keyboard-returnable without intercepting transport shortcuts. Layout-specific Flutter page-storage keys in a bucket owned by this authenticated page preserve the desktop grid and narrow list scroll offsets while their Scaffold is locally replaced; the bucket disappears with the page and does not cache Provider data or add a scroll state domain. The page retains one Flutter focus node for only the last opened provider/opaque playlist identity; after any supported return, it reattaches and requests focus only if that row still exists, preserving Enter-based navigation without retaining collection data. It requests pages of at most 100 rows, advances offsets by the raw response length, rejects mismatched or non-advancing pages, and deduplicates only exact provider/opaque track identities at page boundaries. Initial failure replaces the page; retryable append failure preserves existing rows and has a separate retry state. Explicit first-page refresh preserves the complete loaded Track and pagination snapshot, blocks concurrent append work, and replaces it only after a valid page-zero result; retryable failure keeps the snapshot, while account/replacement/rejection clears it. Retryable non-account failures offer retry/back without discarding the retained session; account-state failures alone offer sign-in recovery. Full-screen failure copy is one isolated live region, while its actions stay independently focusable. Restart/back/dispose cancels the current handle and suppresses late generations, while explicit rejection still follows shared serialized-vault cleanup. Desktop and narrow layouts render track display data, refresh/load-more progress, and a truthful terminal state. Playlist cards and Track actions expose one concise semantic label rather than repeating their decorative artwork, visible metadata, row number, and duration; semantic tap remains explicit, and narrow Track rows retain semantic long press. Track rows expose bounded “Play from here” and “Add to queue” actions through desktop right-click, the Context Menu key or Shift+F10, and mobile long press. Validated Album context adds “Open album”; validated Artist context opens one credit directly or requires explicit selection among every collaboration credit. The authenticated page places retained Artist and Album pages above owned, recommended, and Search-origin playlist details; an Artist may nest the existing Album page, so platform/AppBar return restores Album → Artist → the same playlist controller, loaded rows, pagination, and playback owner without a navigation framework. Playback snapshots the exact loaded rows and selected position; append delegates the unchanged provider-neutral Track model to the Rust-backed positional queue, so duplicate identities remain valid and Flutter never mutates a shadow queue. The synchronous queue result determines immediate added/failed feedback; if the first push selects current, its media resolution and playback continue independently and can still report their own truthful state.

The lyric protocol client now has one bounded `PlayLyricInfo/GetPlayLyricInfo` operation using the verified `songMid`, requested song type, QRC, translation, romanization, and encrypted representation flags. It validates global/named codes and representation flags, caps the HTTP body at 2 MiB, ciphertext at 1 MiB per track, decompressed text at 2 MiB, lines at 10,000, and timed segments at 100,000. Cloud QRC decryption uses the QQ-compatible DES D-E-D behavior adapted with its MIT notice plus bounded zlib/UTF-8 decoding. A real XML reader extracts and entity-decodes `LyricContent`; hand-written bounded scanners parse QRC absolute-millisecond line/segment pairs and auxiliary LRC timestamps. Live raw, encrypted, and plaintext bodies never enter diagnostics or retained fixtures; offline tests use independently generated, project-authored non-lyrical ciphertext.

The first lyrics Domain boundary represents one opaque `TrackId`, at least one synchronized original line, and optional timed segments within each line. Line and segment timing is unsigned milliseconds with checked start-plus-duration; source order, gaps, overlaps, zero durations, spacing segments, and segments outside the nominal line interval remain representable because current QRC evidence does not justify normalization. Optional translation and romanization attach to original lines only after Provider mapping establishes an exact start-time match. `LyricsProvider` returns this provider-neutral model or coarse authentication, availability, transport, service, structural, or replacement failures. QQ encryption, XML/QRC parsing, raw response metadata, playback position, and presentation state remain outside Domain and the Provider contract.

`QQMusicProvider` shares structural validation of `track:<id>:<primary-type>:<song-mid>:<file-media-mid-or->` across media and lyrics without exposing that identity grammar. Lyrics use the primary song type and song MID. Media uses the song MID plus optional file-media MID, while the vkey request's `songtype` is the evidence-backed constant zero rather than the unrelated playlist `songtype` field. The Provider preserves every original line and segment, attaches translation or romanization only when exactly one auxiliary row has the same start millisecond, and leaves unmatched or ambiguous rows absent instead of inventing fuzzy alignment. It rechecks the exact credential after the lyric await and clears it only for an explicit credential-rejection code.

The Bridge exposes synchronized lyrics through one single-use `QqMusicLyricLoadHandle`. Its input is the unchanged provider/opaque track identity; its output contains only provider-neutral line text, absolute millisecond line and segment timing, optional translation/romanization, or a coarse typed failure. `run`, exact `cancel`, and `isActive` own the lifecycle, and cancellation drops the losing Provider/network future. The handle and Rust result diagnostics expose only counts, timing, flags, and coarse state—not opaque identity or lyric text. Playback position and active-word selection remain Dart presentation concerns and are not part of this Bridge operation.

The Dart lyric gateway defensively validates nonempty documents, checked 32-bit millisecond timing, unambiguous success/failure shape, and nonempty optional auxiliary text before freezing the accepted lines and segments. Explicit credential rejection alone uses the same serialized vault cleanup boundary as library and playback; availability and transient failures retain the credential. A short-lived lyric controller owns loading/retry/account/error presentation state and exact operation cancellation across track replacement, clear/sign-out, and disposal. It suppresses every late generation and derives active presentation from real playback milliseconds: line and segment intervals are left-closed/right-open, gaps select nothing, overlaps select the later start, and equal starts select the later source-order entry. Segment progress is computed only inside the selected line and segment. Application composition passes the same underlying vault to authentication, library, detail, media, and lyric gateways. Since the lyric surface is not yet present to offer an account action, explicit lyric rejection or rejection-cleanup failure leaves the authenticated page through its existing sign-in reset callback; unavailable and transient failures do not.

`QueuePlaybackController` remains the single coordinator for Rust queue selection and foreground playback. It can own one lyric controller, starts lyrics only when the provider/opaque current Track identity changes, forwards current-session position updates, and clears/disposes lyrics with queue ownership. Duplicate queue positions carrying the same Track identity reuse the same lyric document; no parallel queue, timer, or playback state machine is introduced.

The now-playing surface opens this same controller in an adaptive lyric panel: widths below 600 use a tall modal bottom sheet and wider windows use a bounded dialog. The panel truthfully distinguishes idle, loading, unavailable, retryable/terminal error, account, and content states. Unavailable, error, and account-state title/explanation are isolated semantic live regions after asynchronous loading, while the idle prompt is not announced as an alert and recovery controls stay separate actions. It always preserves the Provider-mapped canonical line; timed segments replace the displayed original only when their exact concatenation is lossless, otherwise they appear as a separate timing row. The selected line and each segment's gradient progress derive only from controller position. Presentation-local follow state brings each newly active line into view, uses a bounded estimate before exact visibility when a seek jumps beyond lazily built rows, pauses as soon as the user scrolls, and exposes an explicit resume action; a replacement lyric document restores default following. When the existing playback controller reports seek available, each line exposes one tap/keyboard semantic action that delegates its exact Domain start millisecond to `seekToMs`; listening to that controller removes the action immediately for stopped, loading, completed, or otherwise unseekable state. Translation and romanization remain optional presentation text. The panel does not parse QRC, fetch data, estimate playback time, own playback, or duplicate account decisions.

Read-only Track comments are a separate provider-neutral capability, not part of playback or a generic social model. `QQMusicClient` sends one bounded anonymous legacy song-comment request using the Provider-owned positive numeric Track identity, zero-based page number, and fixed page size. It keeps first-page hot comments separate from newest comments, treats current numeric-or-text comment identity as bounded provider-opaque data, validates total/count/page bounds and bounded author/content fields, and filters the live-evidenced present-but-blank deleted/non-displayable shape only from newest rows. Continuation still advances from the raw returned-row count and page size rather than the filtered display count; zero raw rows are terminal. User-generated content and identifiers stay out of diagnostics. `QQMusicProvider` alone parses the opaque Track identity and maps comment IDs, author display name, plain text, Unix time, and praise count into the small Domain contract. The Bridge exposes one single-use cancellable page handle over unchanged provider/opaque Track identity and coarse failure categories. Flutter owns first/empty/error/retry/append/cancel/stale/disposal state and deduplicates opaque comment identity while preserving the protocol page cursor. Expanded Now Playing opens a compact bottom sheet or bounded desktop dialog over the existing playback shortcut/controller owner; closing or comment failure cannot replace Queue, lyrics, playback, credential, or retained navigation state. Posting, liking, replying, reporting, avatars, rich comment media, and a generic social framework remain absent.

## Playback and storage

Track-associated MV is a separate bounded provider-neutral capability. `QQMusicClient` first sends one exact anonymous `music.pf_song_detail_svr/get_song_detail_yqq` request for the Provider-owned song MID and accepts only the correlated optional VID. When present, it combines `video.VideoDataServer/get_video_info_batch` metadata with `music.stream.MvUrlProxy/GetMvUrls`, requires the exact requested VID, bounds every display/source field and response body, and selects the first successful HTTPS MP4 in evidenced file-type order 40, 30, 20, then 10. No associated VID is a successful unavailable result; a correlated MV without a supported source remains distinct from network, service, and structural failures. HLS, cleartext sources, related videos, and diagnostics containing Track/MV identity, content, or source URI remain absent.

`music-domain` represents only provider-scoped opaque MV identity, bounded title and credited Artist names, optional HTTPS artwork, optional positive duration, one secret-bearing HTTPS MP4 source, and a coarse quality. `TrackMusicVideoProvider` accepts the unchanged opaque Track identity, while `QQMusicProvider` alone parses QQ identity and maps the protocol result. The Bridge exposes one single-use cancellable `TrackMusicVideoLoadHandle` and provider-neutral result; its diagnostics reveal only coarse state. Flutter defensively validates the generated envelope and URI shape without learning QQ request or identity grammar.

Flutter pins `media_kit` behind a project-owned MV-only engine/session boundary. A session owns one plugin player, video controller, state subscriptions, project Material controls, and terminal disposal; plugin objects and causes do not enter controller state, while the provider-neutral source is handed only to this adapter and remains absent from diagnostics. The existing `audioplayers` music path and Rust positional Queue remain authoritative. Before MV play/resume, the coordinator pauses playing music or stops an in-flight music activation; later music activation or Track replacement disposes MV. Closing, failure, or navigation never auto-resumes music. Expanded Now Playing opens this session in a compact bottom sheet or bounded desktop dialog and otherwise retains the same Queue, lyric, catalog, and navigation state. Fullscreen, picture-in-picture, background video/audio, quality selection UI, caching, downloads, and a generic arbitration framework remain absent. A packaged Linux integration proves synthetic local H.264 decode, pause/seek/resume, while Linux Release and Android x64 Debug prove native packaging; none proves live QQ source playback or other target runtimes.

The first playback protocol foundation now exists in `QQMusicClient`. One bounded unauthenticated CDN-dispatch operation validates HTTP(S) bases and cache/refresh TTLs; a second bounded authenticated `UrlGetVkey` operation requests only the cross-validated standard MP3 filename. With `file.media_mid`, the filename is `M500 + file-media-mid + .mp3`; without it, the independently agreed fallback is `M500 + song-mid + song-mid + .mp3`. The request always sends `songtype: [0]`. It requires one matching item, a matching returned filename, a zero item result, and a relative path that cannot replace the dispatched authority. Source URI diagnostics are redacted and validity is the smaller CDN/vkey TTL. The client preserves unknown item codes only as protocol-level unavailable outcomes and does not infer payment, region, or copyright reasons.

`music-domain` now represents an immediate provider-neutral source as its opaque `TrackId`, secret-bearing URI, `Mp3`/`Standard` labels, and positive validity in seconds. The URI remains accessible only for playback handoff and is redacted from diagnostics. `provider-api` exposes one deliberately narrow standard-media operation and typed authentication, availability, network, service, structural, core, and account-replacement failures.

`QQMusicProvider` alone parses `track:<id>:<primary-type>:<song-mid>:<file-media-mid-or->`. It runs dispatch before vkey, rechecks the exact authenticated credential after both awaits, and signs out only on explicit credential rejection for that candidate. It maps no QQ filename, vkey, CDN list, or raw result code into Domain.

The Bridge exposes this operation through one single-use `QqMusicMediaResolutionHandle`. Its input carries provider and opaque track identity; its success output contains only URI, format, quality, and validity, while its failure output is coarse and typed. The handle owns exact cancel/run/isActive lifecycle, drops the losing Provider/network future, and redacts both opaque identity and source URI from Rust diagnostics. The generated Dart DTO deliberately has no generated string representation.

The Flutter playback edge pins `audioplayers` 6.8.1 behind a project-owned `ForegroundAudioEngine`/per-source session boundary. Every remote load creates a fresh plugin player, so replacing a source can detach and dispose the entire old event authority. The session exposes play, pause, bounded millisecond seek, bounded `0..1` volume, stop, position, and disposal without exposing the plugin object. The adapter exposes only coarse load/playback/core failures, and disables the plugin's global logger before creating a player because its upstream exception string includes `player.source`. No source URI or upstream cause enters controller state or diagnostics.

`ForegroundPlaybackController` owns only short-lived single-track presentation lifecycle: loading, playing, paused, stopped, completed, or coarse error. Each session also maps the plugin's frame-driven position stream into nonnegative integer milliseconds. Seek is accepted only for the exact playing or paused session; concurrent attempts retain only the newest completion, position callbacks are ignored while it is pending, and replacement/dispose invalidates it. One foreground volume value remains in this Dart controller across source replacement, is applied before each fresh session plays, and converges to the newest value after overlapping completions; an old session failure cannot cross into its replacement. A new source and explicit stop reset position to zero; source replacement, stop, failure, and dispose detach the exact state, failure, and position subscriptions before terminal cleanup. Generation plus session identity suppress every late callback, and `TrackPlaybackController` forwards current-session position/volume notifications without estimating time itself. It enables seek only when the selected Track has a positive duration and clamps the requested millisecond to that duration. Cleanup errors cannot revive or block a replacement. A packaged Linux integration proves local-file lifecycle plus loopback remote-MP3 state, volume, positive-position events, and byte-range-backed seek through the project adapter.

`RustMediaResolutionGateway` adapts the generated media handle into a Dart-owned single-use operation. It forwards provider plus opaque track identity unchanged, validates that Bridge success contains exactly one HTTP(S) source with authority and positive validity, maps every coarse failure without collapsing unavailable into network/service failure, and uses a redacted `ResolvedPlaybackSource` string representation. Explicit credential rejection alone enters the same nested shared `SerializedCredentialVault` queue used by authentication/library cleanup.

`TrackPlaybackController` composes exactly one resolution operation with the foreground controller. It owns resolving/loading/playback/error presentation state and the selected track's existing display model, but never parses identity or retains the resolved URI. Replacement, stop, and dispose cancel the current resolution handle and advance a generation before delegating playback cleanup. A current success URI is handed directly to `ForegroundPlaybackController`; resolution failures remain separate from engine failures.

The authenticated `UserLibraryPage` owns one queue/playback/lyric coordinator so those lifecycles survive local library/detail navigation and are disposed together when the authenticated surface leaves. Its presentation-only primary shell defaults to a responsive Home backed by bounded real data from the existing user-library and public recommended-playlist controllers. Home and Discover share one recommendation controller/request; Home shows at most eight rows from each source with independent loading/empty/error states, opens the existing playlist-detail route directly, and restores the exact originating card on return. Home, Discover, Search, and Library share one retained `IndexedStack`, exposed through an official Material extended labeled sidebar at wide desktop widths, a narrower labeled `NavigationRail` at medium widths, and `NavigationBar` at compact widths without introducing a navigation framework. A small typed presentation state records the active primary destination, selected Library subsection, visited retained roots, and ordered local detail routes. Back pops one typed detail, then returns a Library subsection to Playlists, then a peer destination to Home; it no longer reconstructs route priority from unrelated nullable fields. Search and Discover can omit their nested Scaffold chrome when embedded; their controllers and loaded state remain mounted across primary-destination changes and window resize. Library adds a smaller adaptive Playlists/Albums/Artists selector above another lazy retained stack: Playlists keeps its existing controller, visited favorite roots keep their independent controllers and scroll/paging/failure state, and embedded roots omit their duplicate Scaffold/Now Playing while details remain overlays above the exact selected section. Library loading remains independent, while an explicit authenticated-account failure replaces every primary destination so private-session rejection cannot be hidden by Home. One structurally stable shortcut wrapper prevents destination/back-state changes from disposing that retained tree. The composition root constructs authentication plus three immutable, explicit post-authentication dependency groups—Library/Catalog, Discovery/Search, and Playback—and keeps the credential-bearing gateways over one shared serialized vault. These groups are constructor-injected values, not a service locator or hidden global. Detail rows send their existing provider/opaque identities into queue replacement before media and lyric resolution. Local Artist, Album, Playlist, Ranking, current-Track catalog, and expanded Now Playing pages are typed route entries above the retained root. Return removes exactly the top entry while underlying controllers remain mounted; Now Playing catalog and expansion callback scopes remain bounded to prevent recursive actions. Account-state media failures provide an explicit sign-in reset, while an explicit lyric credential rejection uses the same reset automatically. This does not prove real authenticated QQ playback or lyric loading, cleartext-source policy, or another target runtime.

The reusable queue foundation is `music-domain::PlaybackQueue`. It owns ordered `TrackSummary` entries, including optional provider-neutral Album context and credited Artist context, and exactly one current position whenever non-empty. Public Queue order, selection, and removal remain positional, and duplicate `TrackId` values are deliberately retained because repeated entries can express user intent. The same Domain owner now carries session-local sequential/shuffle order plus repeat off/all/one semantics. Shuffle keeps a separate randomized position cycle anchored at current rather than reordering the public Queue; selection, replacement, or membership mutation rebuilds that cycle around the resulting current position. Repeat one affects automatic completion while manual navigation follows the active order; repeat all wraps sequential order or begins another shuffle cycle without immediately replaying the prior cycle's last position. Mode changes never request media restart, while same-position repeat completion explicitly does. The Bridge initializes non-security shuffle entropy, exposes only typed mode state/setters and coarse playback requests, and does not compute traversal. The model still has no Provider fetching, media URI, plugin state, presentation state, persistence, background lifecycle, or automatic pagination.

The Bridge exposes each queue as a Dart-owned Rust-opaque `PlaybackQueueHandle`, not a global service. Synchronous replace/push/select/advance/rewind/complete/remove/clear commands lock only this small in-process Domain object and return an immutable provider-neutral snapshot plus `currentChanged`; the latter distinguishes a positional current replacement from an unrelated removal. Track DTO conversion validates Domain identity/display invariants and optional same-Provider Album plus credited-Artist identity before mutation, and invalid track/position or poisoned-core failures are coarse and typed. Snapshots preserve duplicates and both catalog contexts while exposing no media source. The generated boundary has passed a packaged Linux FFI mutation smoke.

`RustPlaybackQueueGateway` is the only Dart adapter for generated queue DTOs. It validates exactly one snapshot or typed failure, all track display/identity invariants, the non-empty/current relationship, and `hasPrevious`/`hasNext` consistency. It keeps list data immutable and redacts diagnostics. Native handle creation is lazy so signed-out presentation and FFI-free widget tests do not touch Rust before application initialization.

`QueuePlaybackController` retains the last valid snapshot when a Bridge command fails and delegates every list mutation and playback-mode change back to Rust. It starts a new `TrackPlaybackController` operation only when the Bridge explicitly requests playback; current removal therefore plays the Domain-selected successor/predecessor, unrelated removal or mode change does not restart audio, and repeat-one completion can replay the same position. One completion notification calls Rust completion once, advances or replays and plays the returned current item, or leaves the terminal completed item selected. The authenticated library page owns this queue/playback composition across local list/detail navigation and disposes both at sign-out. Activating a detail row explicitly replaces the queue with the detail controller's rows loaded at that moment and selects the exact row position. Later page loads do not mutate that playback queue until another row activation.

The adaptive now-playing surface consumes the queue controller and exposes bounded previous/next, single-track play/pause/retry/stop, authoritative shuffle/repeat, account reset, lyrics, Queue, comments and volume affordances, and exact elapsed/duration progress when Track duration is known. It renders the current Track's existing provider-neutral artwork URI with a local album placeholder; loading and playback errors are compact overlays, and image failure cannot replace playback state. When the current queue value already carries validated same-Provider Album or credited-Artist context, that artwork becomes one touch-sized, keyboard-focusable catalog action. A single destination opens directly; multiple destinations use a compact bottom sheet or bounded desktop dialog. Wide layout presents large artwork beside the existing synchronized lyric panel; compact layout stacks bounded artwork above that panel. Routes above each callback scope expose no recursive action. The existing artist/status copy remains an isolated semantic live region, so meaningful stage or coarse-error changes can be announced without merging the playlist header, Track title, or progress into the notification. Slider movement owns only a temporary visual preview and commits one bounded native seek or volume update when released; unknown duration renders no invented progress. One reusable Flutter shortcut scope maps hardware media keys plus `Ctrl+Space`, `Ctrl+Left`, and `Ctrl+Right` to the same queue/controller actions across local library/detail navigation and while any adaptive queue, lyric, volume, comment, catalog-selection, or immersive route owns focus; its authentication guards remain identical to visible controls. Credential semantics and serialization remain in Rust. `flutter_secure_storage` is a platform integration edge only; it stores one opaque versioned document and cannot declare a user authenticated.
