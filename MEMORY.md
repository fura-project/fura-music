# Project Memory

- The repository started from a single MIT `LICENSE` commit (`f439866`) on 2026-08-25; no legacy architecture or implementation needs preservation.
- The product contract is QQ Music-first. Additional providers are for proven fallback or local-library needs, not breadth marketing.
- Divide Flutter and Rust by lifecycle: reusable product/domain behavior belongs in Rust; presentation-driven state belongs in Dart.
- Normal runtime communication is an in-process typed bridge. Do not introduce a localhost API sidecar.
- External QQ Music behavior must be isolated behind `QQMusicClient`; project domain models must not become aliases for raw response models.
- QQ direct Artist Search uses the Desktop type-1 `music.search.SearchCgiService/DoSearchForQQMusicDesktop` envelope with no top-level `comm`; pagination lives in `data.meta`, results in `data.body.singer.list`, and a usable existing Artist route requires positive numeric ID plus safe MID and nonblank name. Keep query, Artist content, and tracing metadata out of diagnostics and long-lived models.
- QQ direct Album Search uses the same no-`comm` Desktop envelope with type `2`, pagination in `data.meta`, and rows at `data.body.album.list`. The existing Album route requires a positive numeric `albumID`, safe `albumMID`, and nonblank `albumName`; optional artwork, release, Artist, and tracing fields are not protocol identity.
- QQ current rankings use anonymous named-key `music.musicToplist.Toplist/GetAll` and `GetDetail` calls without top-level `comm`. List groups live at `data.group`; detail metadata lives at `data.data` and Tracks at `data.songInfoList`. Keep `period` optional, keep numeric `topId` opaque outside `QQMusicProvider`, and do not treat the current-detail route as historical-period support.
- QQ direct Playlist Search uses the no-`comm` Desktop type-3 `music.search.SearchCgiService/DoSearchForQQMusicDesktop` envelope; rows live at `data.body.songlist.list`, `dissid` is a numeric string, and pagination lives in `data.meta`. A nonterminal service page can be shorter than the requested size, so follow `nextpage` rather than deriving completion from row count. Keep query, playlist content, and provider identity out of diagnostics and opaque outside `QQMusicProvider`.
- QQ Radar uses authenticated `music.recommend.TrackRelationServer/GetRadarSong` with `Page`, `ReqType: 0`, empty `FavSongs`/`EntranceSongs`, credential-bearing `comm`, and the existing Cookie. Tracks live at `data.VecSongs[*].Track` and continuation at `data.HasMore`. A bounded anonymous two-page probe returned ten rows on page 1 rather than the older documented one-seed shape and one identity overlap across pages, so never encode first-page row count and deduplicate provider/opaque identity while advancing only by `Page`/`HasMore`. Anonymous structure does not prove personalization or recommendation quality.
- QQ regional new Albums use anonymous `newalbum.NewAlbumServer/get_new_album_info` with `area` 1–6, zero-based `start`, and `num`; rows and numeric total live at `data.albums` and `data.total`. Advance by the raw row count before provider/opaque Album deduplication, validate nested Album and credited Artist identity, and keep the six numeric area values inside the QQ client/provider boundary. Bounded anonymous evidence across every region retained no returned catalog content and does not prove live application compatibility.
- QQ canonical Album metadata uses anonymous `music.musichallAlbum.AlbumInfoServer/GetAlbumDetail` with the existing safe MID under request key `albumMId`. Current fields live under `data.basicInfo`, `data.company`, and `data.singer.singerList`; validate returned `albumMid` exactly, use actual keys such as `albumID`, `albumName`, `tranName`, and `publishDate`, and bound the description separately from short display text. Metadata has an independent cancellable lifecycle and must never hide Album Tracks or queue actions when it fails.
- QQ favorite Albums do not use the tempting `music.musicasset.AlbumFavRead/CgiGetAlbumFavInfo`: a current real-account record returned `80000` plus a zero structure despite existing favorites. Use the authenticated legacy `fav/fcgi-bin/fcg_get_profile_order_asset.fcg` route with `reqtype=2`, numeric user identity, credential Cookie, and inclusive `sin`/`ein`. Accept the observed lower/upper Album field casings and boolean-or-0/1 `has_more`; only directly evidenced global code `4000` means credential rejection, while other global/subcodes retain the session.
- Never commit cookies, credentials, tokens, QIMEI identifiers, or user-derived fixtures.

- QQ Music restore must validate upstream: local `musickeyCreateTime + keyExpiresIn` can prove expiry but cannot prove validity. Current independent implementations agree on credential-rejection codes `1000`, `104400`, and `104401`; do not turn unrelated network/protocol failures into logout.
- The WeChat web QR bootstrap parameters were independently matched in L-1124 and ylw1997 implementations and passed an unconfirmed live request on 2026-08-25. Treat the returned UUID and image as transient sensitive session material: never persist or log them. This test proves bootstrap compatibility only, not polling, credential exchange, or login.
- On 2026-08-26 the user manually completed an authorized WeChat scan, populated the authenticated library/detail surface, fully restarted the app, and returned without scanning again. No account material or content was supplied or retained. This proves the successful credential exchange and restore path for that login shape. Playback then failed for every attempted ordinary and VIP track until the `songtype` mapping fix; playback/queue/lyrics still require a post-fix observation.
- WeChat web QR polling uses `lp.open.weixin.qq.com/connect/l/qrconnect`: 408 waits for scan, 404 is scanned awaiting confirmation, 405 carries an OAuth code, 402 is expired, and 403 is refused. An unscanned live poll returned 408 on 2026-08-25. The OAuth code is sensitive, and this evidence does not yet prove credential exchange or session cancellation behavior.
- QR lifecycle cancellation is generation-based in `WechatQrLoginCoordinator`: replace, cancel, session drop, coordinator drop, and the shared 180-second deadline wake the lifecycle watcher and drop the losing create/poll/exchange future. Always recheck the generation after an await; otherwise a late 405 can authenticate a superseded UI session. Allow three consecutive transport failures and end on the fourth; any reached protocol response resets the count, and non-transport errors must remain precise.
- WeChat credential exchange currently uses the named `music.login.LoginServer.Login` key and lightweight `ct=11` musicu comm validated by a no-account invalid-code probe on 2026-08-25 (global 0, login 1000). Successful responses often omit `loginType` and may set numeric `musicid` to 0, so preserve channel type 1 and prefer nonzero `str_musicid`. Retain refresh fields, redact them, and never treat the invalid-code probe as proof of a real successful login.
- Flutter receives QR auth through an FRB `RustOpaque` handle with only `advance`, `cancel`, and `isActive`; the challenge contains image format/bytes and updates contain coarse enums. Keep generation-specific cancellation beside the locked session so cancel remains possible during a long poll and a stale handle cannot cancel a replacement. Never add UUID, OAuth code, Credential, music key, or refresh fields to generated Dart models.
- The Dart `LoginController` owns only presentation stages and polling intent. It must cancel both pending QR creation and active opaque sessions on restart/dispose, compare its local generation after every await, auto-retry only typed network failures, and stop for protocol/upstream errors until user action. Bridge start-attempt IDs exist only to make pre-session cancellation exact; they are not QQ/WeChat identifiers.
- Credential persistence uses top-level `flutter_secure_storage` 10.3.1 only as a native vault adapter (ADR 0003), while Pub retains compatible current federated platform packages where constraints allow. Version 11.0.0 is not buildable on the current supported Flutter/AGP line because it requires an unavailable integer compile-SDK 37 target; do not fork the plugin or override its declared SDK just to produce an APK. Rust owns the versioned document and invariant validation; Dart sees one short-lived opaque byte buffer, Base64-encodes it for the string API, writes one namespaced key, and zeroes the buffer. Never expose individual fields to generated Dart or treat storage presence as authentication.
- Android backup is disabled for encrypted credential storage. Apple storage is device-local, non-synchronizing, and requires the checked-in Keychain entitlements. Linux libsecret 0.21.7 with KDE Secret Service passed a live randomized non-account write/read/delete integration on 2026-08-25; Android 16 x64 passed the same bounded write/read/delete/absence contract on 2026-08-26. After the Android storage compatibility change, the real signed-out app performed one empty legacy-algorithm migration on first launch and did not repeat it after force-stop/relaunch. Apple and Windows runtime targets remain TD-004.
- Startup vault import must preserve four Rust states: signed out, pending server verification, locally expired, and authenticated. Storage presence, successful JSON decoding, and a future local expiry timestamp never set the authenticated state. Dart distinguishes corrupt Base64, unsupported documents, platform access failure, and core failure, zeroes its mutable input after import, and never auto-deletes the vault entry.
- Startup server verification uses the named `music.UserInfo.userInfoServer/GetLoginUserInfo` musicu request with the credential in both lightweight `ct=11` comm fields and the request Cookie. Both global and named-result codes must be zero. Only independently observed codes `1000`, `104400`, and `104401` mean credential rejection; transport, HTTP, malformed response, and other upstream codes retain the Rust candidate for retry.
- Restore-verification attempt IDs are exact cancellation authority, like QR start generations: reserve before async work, recheck the same ID and candidate after every await, and let a new QR login supersede both. Explicit server rejection clears the Rust state and asks the Dart vault edge to delete; a vault deletion failure stays visible and must not be described as successful cleanup.
- Manual sign-out is a local ordered operation, not a guessed QQ Music logout request. Clear/cancel Rust credential authority first, then delete the single shared serialized-vault entry; never delete the vault when Core could not transition. A vault failure means Core is signed out but restart may restore the saved copy, so keep that state explicit and retryable. Stop foreground playback while cleanup is pending, and keep late verification/request completions unable to revive the credential.
- Share one `SerializedCredentialVault` beneath authentication and library gateways. Rejection cleanup can outlive controller cancellation; without cross-gateway ordering, a late library delete can remove a newly written QR credential. Independently wrapped gateways remain ordered when their inner vault is the shared serialized instance.
- QQ Music account-owned playlists use `music.musicasset.PlaylistBaseRead/GetPlaylistByUin` with the numeric music ID serialized as a string. Response rows carry both `tid` (playlist identity) and `dirId` (account directory identity); preserve both because built-in liked songs use `dirId: 201` and a special detail request rather than treating 201 as a generic `disstid`.
- Do not describe `GetPlaylistByUin` as the full user library. Favorited playlists use `music.musicasset.PlaylistFavRead/CgiGetPlaylistFavInfo` with encrypted UIN and pagination; implement and fixture-test that separate path before merging collections.
- Favorite playlist pages use `v_list`, `total`, and `hasmore`; accept only boolean or numeric `0`/`1` continuation values, cap page size at 100, and fail before transport when the credential has no nonblank encrypted UIN. Keep page iteration and non-advancing-page protection in the Provider rather than hiding a loop in `QQMusicClient`.
- Complete QQ user playlists load owned rows first, then at most ten 100-item favorite pages. Advance by raw page length before deduplication, reject an empty page that still says `hasmore`, deduplicate owned/favorite rows by QQ playlist ID, and recheck the exact credential after every await. The 1,000-favorite safety ceiling is TD-005.
- Domain `PlaylistId` contains a stable provider plus a provider-owned opaque value. QQ encodes owned summaries as `owned:<tid>:<dirId>` so later detail routing can recover both identities; Flutter and generic domain code must never parse that format.
- User-library awaits must recheck the exact authenticated credential before returning rows or clearing state. A late old-account response maps to `Replaced`; only an explicit rejection for the still-current credential clears authentication, while network and non-rejection upstream failures preserve it.
- Flutter receives the complete user-playlist request through a single-use RustOpaque handle with `run`, `cancel`, and `isActive`. Cancellation uses a retained `Notify` permit and drops the losing Provider/network future; concurrent `run` is explicit `AlreadyRunning`. The DTO contains provider/opaque ID, title, optional artwork/count, and coarse failures only.
- The Flutter library surface presents the combined Provider result as “Your playlists”. Rows may pass provider/opaque IDs unchanged into playlist-detail loading, but Flutter must never parse QQ identity. Structural or safety-limit library failures show no partial list.
- Ordinary playlist detail and built-in liked songs share `music.srfDissInfo.DissInfo/CgiGetDiss` but not identity parameters: ordinary uses `disstid` and `dirid: 0`; liked songs uses `disstid: 0`, `dirid: 201`, and `enc_host_uin`. Both page with `song_begin/song_num`. Require global and named-result codes, but validate the nested data code only when present because current liked-songs fixtures omit it.
- Playlist detail stays paged through `PlaylistDetailsProvider`; do not replace it with a hidden all-tracks loop. Only `QQMusicProvider` parses `owned:<tid>:<dirId>` / `favorite:<id>` and constructs QQ track opaque IDs. Domain, Bridge, and Flutter must not extract song ID, MID, or type from those strings.
- The playlist-track Bridge follows the existing single-use RustOpaque lifecycle: begin with provider/opaque playlist ID plus offset/size, then run/cancel/isActive. It forwards provider-neutral page/track DTOs and coarse failures only; Dart owns presentation pagination and must treat every track opaque ID as indivisible.
- Playlist detail navigation keeps the library controller alive and owns a separate paged controller. Back/dispose must cancel the active detail handle and suppress late results. Advance the protocol offset by raw page length before exact provider/opaque-ID deduplication; retain loaded rows on retryable append failure, but replace the page on authentication/replacement failures.
- Current standard media resolution uses `music.vkey.GetVkey/UrlGetVkey` plus separate `music.audioCdnDispatch.cdnDispatch/GetCdnDispatch`. The playlist response's `songtype` is not the vkey parameter: an anonymous 20-row probe reproduced 20/20 `101404` when forwarding observed value 13, while zero restored nonempty outcomes. Always send `songtype: [0]`. Retain optional `file.media_mid`; build `M500 + file-media-mid + .mp3` when present and the independently agreed doubled-song-MID fallback when absent. Accept only a matching returned MID/filename and a relative path on an authority returned by dispatch. Treat `purl`/vkey as short-lived secret-bearing data and never infer restriction reasons from raw item codes.
- Only `QQMusicProvider` may parse `track:<id>:<primary-type>:<song-mid>:<file-media-mid-or->` for media resolution and lyrics. It must recheck the exact credential after each await; only explicit rejection clears that candidate. Domain/Bridge/Flutter keep the identity opaque, and all diagnostics must redact the resolved source URI.
- The media Bridge is a single-use `QqMusicMediaResolutionHandle`: Dart supplies provider plus opaque track identity and receives URI/format/quality/validity or a coarse failure. Cancel must drop the losing Provider future. Keep URI and opaque identity out of Rust Debug, and do not add generated or handwritten string representations that expose the source.
- M1 foreground playback selected exact `audioplayers` 6.8.1 behind a future project-owned adapter. Its endorsed desktop/mobile plugins keep the initial dependency boundary smaller than `media_kit` or `just_audio` plus desktop adapters, and its lack of a playlist prevents premature queue ownership. Linux requires GStreamer core/app/audio development modules and MP3 runtime plugins; a packaged local MP3 lifecycle passed there, not on other targets.
- `audioplayers` upstream `AudioPlayerException.toString()` includes `player.source`, so `AudioplayersForegroundAudioEngine` must set the global `AudioLogger` level to `none` before constructing any player. Propagate only coarse project failures. Each remote load owns a fresh player/session; replacement, stop, failure, and dispose detach by generation plus session identity before cleanup to suppress late callbacks.
- The Dart media gateway must treat Bridge success as exactly one HTTP(S) source with authority and positive TTL; source plus failure or neither is invalid. Its source/result `toString` stays redacted. Only `credentialRejected` deletes through the app's shared nested `SerializedCredentialVault`; unavailable, network, service, replacement, cancellation, and structural failures retain the vault.
- `TrackPlaybackController` owns one resolution operation plus the foreground controller, not a queue. It forwards provider/opaque track ID unchanged, keeps only the selected display model, and hands a current URI directly to playback. Replacement, stop, and dispose cancel resolution and advance the generation; resolution failure and engine failure stay separate for truthful UI.
- Linux/GStreamer can play a small HTTP MP3 from a server that always returns `200`, while native seek still fails because the source is not byte-seekable. Project loopback seek fixtures must implement a valid single `Range` request with `206`, `Content-Range`, `Accept-Ranges`, and bounded slice length; this is test infrastructure evidence, not permission to rewrite real QQ CDN requests.
- The authenticated `UserLibraryPage` owns one positional queue/playback/lyric coordinator so it survives local list/detail navigation but is disposed on sign-out. Default authentication, library, detail, media, and lyric gateways must share the same serialized vault; otherwise a late explicit rejection cleanup can race a newer login. Now-playing, queue, and lyric surfaces consume only coarse controller state and display metadata, never the resolved URI or QQ identity grammar.
- Playback queue identity is positional, not deduplicated by `TrackId`: intentionally queuing the same provider track twice must retain two entries. Rust Domain owns replacement, selection, bounded navigation/completion, and removal-current semantics; Bridge and Flutter may adapt snapshots but must not reimplement those rules.
- Each playback queue is a Dart-owned Rust-opaque handle, not global Core state. Its Bridge update contains exactly one snapshot or typed failure plus `currentChanged`; invalid DTO/position commands leave Domain state untouched. Flutter should retain the last valid snapshot on failure and start a new media operation only when Domain reports that the positional current entry changed.
- `QueuePlaybackController` is the sole completion composer: one transition into the single-track `completed` stage calls Rust `completeCurrent` once. A changed current starts the returned track; terminal completion stays selected. Queue command failure retains the last valid snapshot and current audio instead of guessing a Dart-side mutation.
- Activating a playlist row snapshots only the detail rows loaded at that moment into the positional queue and selects its exact index. Later pagination must not mutate a running queue implicitly. Use row-position Widget keys rather than opaque TrackId keys because duplicate track identities are valid.
- Queue presentation is only a view over `QueuePlaybackController`: previous/next/select/remove/clear all delegate to Rust snapshots. Narrow now-playing uses two rows and a bottom sheet; wider layouts use one row and a constrained dialog. Do not add Dart list splicing, implicit pagination updates, shuffle/repeat/reorder/persistence, or hidden Provider fetches.
- Modern word-level lyrics use `music.musichallSong.PlayLyricInfo/GetPlayLyricInfo` with `crypt=1`, `qrc=1`, and the verified `songMid` spelling. A successful `lyric` is cloud-QRC hex ciphertext; `trans` and `roma` are independent optional encrypted tracks and may be empty. Decode with QQ-compatible DES D-E-D behavior plus zlib, not an assumed standard 3DES implementation. Parsed QRC uses absolute millisecond start plus duration for both lines and segments; local QMC-wrapped `.qrc` files are outside M1.
- `QQMusicClient::lyrics` owns the authenticated musicu request, bounded QQ-compatible decryptor, XML attribute/entity handling, QRC scanner, and auxiliary LRC parser. It caps response/ciphertext/plaintext plus line/segment counts, uses only project-authored non-lyrical ciphertext fixtures, and redacts all content. Its opt-in anonymous live test passed the actual request/decrypt/parse path on 2026-08-26 but does not prove account-only outcomes or nonempty auxiliary tracks.
- The provider-neutral lyrics Domain preserves source ordering and text, allows evidence-observed empty/spacing timing, and rejects only overflowing timing or an empty successful document. `LyricsProvider` owns opaque track routing; protocol encryption, raw QRC, auxiliary alignment policy beyond exact-start, playback position, and Flutter state must not leak into Domain.
