# Project Memory

- The repository started from a single MIT `LICENSE` commit (`f439866`) on 2026-08-25; no legacy architecture or implementation needs preservation.
- The product contract is QQ Music-first. Additional providers are for proven fallback or local-library needs, not breadth marketing.
- Divide Flutter and Rust by lifecycle: reusable product/domain behavior belongs in Rust; presentation-driven state belongs in Dart.
- Normal runtime communication is an in-process typed bridge. Do not introduce a localhost API sidecar.
- External QQ Music behavior must be isolated behind `QQMusicClient`; project domain models must not become aliases for raw response models.
- Never commit cookies, credentials, tokens, QIMEI identifiers, or user-derived fixtures.
- On the 2026-08-25 local Flutter 3.47.1 user-branch SDK, `flutter analyze` truncates its LSP initialization JSON when this checkout is under a path containing Chinese characters and exits 255. `dart analyze` completes normally and is the local static-analysis command until the SDK issue changes; this does not waive Flutter tests or builds.
- `flutter_rust_bridge_codegen generate` 2.13.0 does not delete generated Dart files when a Rust API module is renamed; search `apps/flutter/lib/src/rust/api` for orphaned files after generation.
- QQ Music restore must validate upstream: local `musickeyCreateTime + keyExpiresIn` can prove expiry but cannot prove validity. Current independent implementations agree on credential-rejection codes `1000`, `104400`, and `104401`; do not turn unrelated network/protocol failures into logout.
- The WeChat web QR bootstrap parameters were independently matched in L-1124 and ylw1997 implementations and passed an unconfirmed live request on 2026-08-25. Treat the returned UUID and image as transient sensitive session material: never persist or log them. This test proves bootstrap compatibility only, not polling, credential exchange, or login.
- WeChat web QR polling uses `lp.open.weixin.qq.com/connect/l/qrconnect`: 408 waits for scan, 404 is scanned awaiting confirmation, 405 carries an OAuth code, 402 is expired, and 403 is refused. An unscanned live poll returned 408 on 2026-08-25. The OAuth code is sensitive, and this evidence does not yet prove credential exchange or session cancellation behavior.
- QR lifecycle cancellation is generation-based in `WechatQrLoginCoordinator`: replace, cancel, session drop, coordinator drop, and the shared 180-second deadline wake the lifecycle watcher and drop the losing create/poll/exchange future. Always recheck the generation after an await; otherwise a late 405 can authenticate a superseded UI session. Allow three consecutive transport failures and end on the fourth; any reached protocol response resets the count, and non-transport errors must remain precise.
- WeChat credential exchange currently uses the named `music.login.LoginServer.Login` key and lightweight `ct=11` musicu comm validated by a no-account invalid-code probe on 2026-08-25 (global 0, login 1000). Successful responses often omit `loginType` and may set numeric `musicid` to 0, so preserve channel type 1 and prefer nonzero `str_musicid`. Retain refresh fields, redact them, and never treat the invalid-code probe as proof of a real successful login.
- Flutter receives QR auth through an FRB `RustOpaque` handle with only `advance`, `cancel`, and `isActive`; the challenge contains image format/bytes and updates contain coarse enums. Keep generation-specific cancellation beside the locked session so cancel remains possible during a long poll and a stale handle cannot cancel a replacement. Never add UUID, OAuth code, Credential, music key, or refresh fields to generated Dart models.
- The Dart `LoginController` owns only presentation stages and polling intent. It must cancel both pending QR creation and active opaque sessions on restart/dispose, compare its local generation after every await, auto-retry only typed network failures, and stop for protocol/upstream errors until user action. Bridge start-attempt IDs exist only to make pre-session cancellation exact; they are not QQ/WeChat identifiers.
- Credential persistence uses `flutter_secure_storage` 11 only as a native vault adapter (ADR 0003). Rust owns the versioned document and invariant validation; Dart sees one short-lived opaque byte buffer, Base64-encodes it for the string API, writes one namespaced key, and zeroes the buffer. Never expose individual fields to generated Dart or treat storage presence as authentication.
- Android backup is disabled for encrypted credential storage. Apple storage is device-local, non-synchronizing, and requires the checked-in Keychain entitlements. On 2026-08-25 Linux libsecret 0.21.7 with KDE Secret Service passed a live randomized non-account write/read/delete integration and confirmed absence in `finally`; non-Linux runtime targets remain TD-004.
- Startup vault import must preserve four Rust states: signed out, pending server verification, locally expired, and authenticated. Storage presence, successful JSON decoding, and a future local expiry timestamp never set the authenticated state. Dart distinguishes corrupt Base64, unsupported documents, platform access failure, and core failure, zeroes its mutable input after import, and never auto-deletes the vault entry.
- Startup server verification uses the named `music.UserInfo.userInfoServer/GetLoginUserInfo` musicu request with the credential in both lightweight `ct=11` comm fields and the request Cookie. Both global and named-result codes must be zero. Only independently observed codes `1000`, `104400`, and `104401` mean credential rejection; transport, HTTP, malformed response, and other upstream codes retain the Rust candidate for retry.
- Restore-verification attempt IDs are exact cancellation authority, like QR start generations: reserve before async work, recheck the same ID and candidate after every await, and let a new QR login supersede both. Explicit server rejection clears the Rust state and asks the Dart vault edge to delete; a vault deletion failure stays visible and must not be described as successful cleanup.
- Share one `SerializedCredentialVault` beneath authentication and library gateways. Rejection cleanup can outlive controller cancellation; without cross-gateway ordering, a late library delete can remove a newly written QR credential. Independently wrapped gateways remain ordered when their inner vault is the shared serialized instance.
- QQ Music account-owned playlists use `music.musicasset.PlaylistBaseRead/GetPlaylistByUin` with the numeric music ID serialized as a string. Response rows carry both `tid` (playlist identity) and `dirId` (account directory identity); preserve both because built-in liked songs use `dirId: 201` and a special detail request rather than treating 201 as a generic `disstid`.
- Do not describe `GetPlaylistByUin` as the full user library. Favorited playlists use `music.musicasset.PlaylistFavRead/CgiGetPlaylistFavInfo` with encrypted UIN and pagination; implement and fixture-test that separate path before merging collections.
- Favorite playlist pages use `v_list`, `total`, and `hasmore`; accept only boolean or numeric `0`/`1` continuation values, cap page size at 100, and fail before transport when the credential has no nonblank encrypted UIN. Keep page iteration and non-advancing-page protection in the Provider rather than hiding a loop in `QQMusicClient`.
- Complete QQ user playlists load owned rows first, then at most ten 100-item favorite pages. Advance by raw page length before deduplication, reject an empty page that still says `hasmore`, deduplicate owned/favorite rows by QQ playlist ID, and recheck the exact credential after every await. The 1,000-favorite safety ceiling is TD-005.
- Domain `PlaylistId` contains a stable provider plus a provider-owned opaque value. QQ encodes owned summaries as `owned:<tid>:<dirId>` so later detail routing can recover both identities; Flutter and generic domain code must never parse that format.
- User-library awaits must recheck the exact authenticated credential before returning rows or clearing state. A late old-account response maps to `Replaced`; only an explicit rejection for the still-current credential clears authentication, while network and non-rejection upstream failures preserve it.
- Flutter receives the complete user-playlist request through a single-use RustOpaque handle with `run`, `cancel`, and `isActive`. Cancellation uses a retained `Notify` permit and drops the losing Provider/network future; concurrent `run` is explicit `AlreadyRunning`. The DTO contains provider/opaque ID, title, optional artwork/count, and coarse failures only.
- The Flutter library surface presents the combined Provider result as “Your playlists”. Rows may pass provider/opaque IDs unchanged into playlist-detail loading, but Flutter must never parse QQ identity. Structural or safety-limit library failures show no partial list.
- Ordinary playlist detail and built-in liked songs share `music.srfDissInfo.DissInfo/CgiGetDiss` but not identity parameters: ordinary uses `disstid` and `dirid: 0`; liked songs uses `disstid: 0`, `dirid: 201`, and `enc_host_uin`. Both page with `song_begin/song_num`. Require global and named-result codes, but validate the nested data code only when present because current liked-songs fixtures omit it.
- Playlist detail stays paged through `PlaylistDetailsProvider`; do not replace it with a hidden all-tracks loop. Only `QQMusicProvider` parses `owned:<tid>:<dirId>` / `favorite:<id>` and constructs QQ track opaque IDs. Domain, Bridge, and Flutter must not extract song ID, MID, or type from those strings.
- The playlist-track Bridge follows the existing single-use RustOpaque lifecycle: begin with provider/opaque playlist ID plus offset/size, then run/cancel/isActive. It forwards provider-neutral page/track DTOs and coarse failures only; Dart owns presentation pagination and must treat every track opaque ID as indivisible.
- Playlist detail navigation keeps the library controller alive and owns a separate paged controller. Back/dispose must cancel the active detail handle and suppress late results. Advance the protocol offset by raw page length before exact provider/opaque-ID deduplication; retain loaded rows on retryable append failure, but replace the page on authentication/replacement failures.
- Current standard media resolution uses `music.vkey.GetVkey/UrlGetVkey` plus separate `music.audioCdnDispatch.cdnDispatch/GetCdnDispatch`. With no separate file MID, both current implementations build `M500 + songmid + songmid + .mp3`; their differing separate-media-MID forms are not authorized. Accept only a matching returned MID/filename and a relative path on an authority returned by dispatch; prefer measured `dl.stream` only when it is in that set. Treat `purl`/vkey as short-lived secret-bearing source data, preserve unknown item result codes only inside the protocol layer, and never infer payment/region reasons without fixtures.
- Only `QQMusicProvider` may parse `track:<id>:<type>:<vkey-type-or->:<song-mid>` for media resolution. It must recheck the exact credential after both dispatch and vkey awaits; only explicit rejection clears that candidate. Domain/Bridge/Flutter keep the identity opaque, and all diagnostics must redact the resolved source URI.
- The media Bridge is a single-use `QqMusicMediaResolutionHandle`: Dart supplies provider plus opaque track identity and receives URI/format/quality/validity or a coarse failure. Cancel must drop the losing Provider future. Keep URI and opaque identity out of Rust Debug, and do not add generated or handwritten string representations that expose the source.
- M1 foreground playback selected exact `audioplayers` 6.8.1 behind a future project-owned adapter. Its endorsed desktop/mobile plugins keep the initial dependency boundary smaller than `media_kit` or `just_audio` plus desktop adapters, and its lack of a playlist prevents premature queue ownership. Linux requires GStreamer core/app/audio development modules and MP3 runtime plugins; a packaged local MP3 lifecycle passed there, not on other targets.
- `audioplayers` upstream `AudioPlayerException.toString()` includes `player.source`, so `AudioplayersForegroundAudioEngine` must set the global `AudioLogger` level to `none` before constructing any player. Propagate only coarse project failures. Each remote load owns a fresh player/session; replacement, stop, failure, and dispose detach by generation plus session identity before cleanup to suppress late callbacks.
- The Dart media gateway must treat Bridge success as exactly one HTTP(S) source with authority and positive TTL; source plus failure or neither is invalid. Its source/result `toString` stays redacted. Only `credentialRejected` deletes through the app's shared nested `SerializedCredentialVault`; unavailable, network, service, replacement, cancellation, and structural failures retain the vault.
- `TrackPlaybackController` owns one resolution operation plus the foreground controller, not a queue. It forwards provider/opaque track ID unchanged, keeps only the selected display model, and hands a current URI directly to playback. Replacement, stop, and dispose cancel resolution and advance the generation; resolution failure and engine failure stay separate for truthful UI.
- The authenticated `UserLibraryPage` owns the single-track coordinator so it survives local list/detail navigation but is disposed on sign-out. Default authentication, library, detail, and media gateways must share the same serialized vault; otherwise a late explicit rejection cleanup can race a newer login. The now-playing surface consumes only coarse controller state and display metadata, never the resolved URI.
