## Exact request chain and ownership

```text

  -> website JS's official Stage 2 paused request
  -> abort + confirmed browser/process/profile cleanup
  -> one Rust Stage 2 HTTPS response
  -> existing strict full-track Standard source validation
```

`AuthenticatedStandardCandidate` remains the single session owner. Non-clone
capture/Stage 1/continuation/Stage 2 tokens retain owner-generation and exact
TrackId. Stage 1 and Stage 2 each have a one-use admission in a fixed two-slot
budget, consumed synchronously before their transport await. Clear/replacement,
same-account relogin, failed/dropped futures and risk/rate stops do not refill
budgets. Late results and stale fulfillment are rejected. The minimal Cookie
session must remain identical between stages; no account identity is inferred
from its mere presence. No Vault or global authenticated state is introduced.

Stage 1 must be a request-stage paused GET on the exact HTTPS songinfo route from

Presentation fields are never identity proof. Unsupported alternate IDs and an

The browser request stays paused while Rust sends the captured URL/headers once.
No signer/profile repair or endpoint construction occurs. Successful Stage 1

## Fulfillment representation contract

The official [Fetch.fulfillRequest schema](https://chromedevtools.github.io/devtools-protocol/tot/Fetch/#method-fulfillRequest)
defines a base64 body and response-header list. The fetched official JSON schema
is retained only in temporary evidence; the exact bounded server body, including
JSON whitespace/order/escaping, is base64-encoded without reserialization. Status
must be 200 and content type must be JSON. Original end-to-end headers, including
the actual CORS policy, are preserved. No Origin/CORS/success fields are invented.

HTTP hop-by-hop framing is not representation content; see
[RFC 9110 section 7.6.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-7.6.1).
reqwest supplies dechunked body bytes, and only recognized connection/framing
headers are omitted for CDP fulfillment. A provided Content-Length must equal
those exact bytes; duplicate/ambiguous framing is rejected. Header count/bytes
and body size are bounded. No alternate decompressor or response repair exists.

Unsupported semantics stop before fulfillment with precise fixed categories:

- non-identity Content-Encoding: `STAGE1_RESPONSE_ENCODING_UNSUPPORTED`;
- Set-Cookie/Set-Cookie2: `STAGE1_RESPONSE_COOKIE_MUTATION_UNSUPPORTED`;
- invalid/ambiguous length, unknown connection options, authentication/redirect/
  refresh/trailer/upgrade semantics, backup-only first-stage media, unsafe or
  inconsistent headers:
  `STAGE1_RESPONSE_REPLAY_UNSUPPORTED`.

These are conservative implementation limits, not observed live blockers. They
must be recorded if encountered at the next separately authorized Human run;
do not discard a header, change the Cookie session or guess a repair to proceed.
Missing/ineffective actual CORS is not corrected by Fura and may leave no observed
Stage 2. Browser JS behavior beyond the supported subset remains unproved live.

### Installed-Chromium root-cause evidence

Chrome 155 and the loopback TLS fixture reproduced the directly adjacent target
compatibility failures before Stage 1:

- service-worker `Runtime.runIfWaitingForDebugger` ended as CDP unavailable;
- dedicated-worker `Fetch.enable` was rejected as an invalid domain command;
- OOPIF `Fetch.enable` was likewise not consistently available;
- transient OOPIF detach can race any in-flight setup command.

The fixed primary classification for the reproduced original-sequence failure is
`CDP_UNAVAILABLE / RESUME_TARGET / SERVICE_WORKER`. The worker/OOPIF results are
additional concrete compatibility defects in the same old unconditional command
sequence. They are not protocol-V2 evidence and do not alter either songinfo
stage.

The interceptor now treats target types according to the domains the installed
browser actually exposes:

- `page`: arm Fetch, Page and Network bypass, establish child auto-attach, then
  resume; only a proved official page/frame may supply accepted capture;
- `iframe` (OOPIF): never accepted as capture provenance and never sent its
  unsupported Fetch command; resume only after the parent page is armed;
- dedicated/shared/service worker: never accepted, never sent unsupported
  Fetch/Page commands, and kept debugger-paused for this bounded gate. A worker
  cannot run and surface a request on the parent page session;
- every browser launch adds an exact `wwwapi.kugou.com -> ~NOTFOUND` Chromium
  resolver fence. Page Fetch pauses the intended official request before DNS;
  an unsupported target has no network route to leak songinfo.

OOPIF churn does not become a silent protocol bypass. If setup reports an invalid
command, a browser-level `Target.getTargetInfo` query must prove that exact target
is absent or detached before the race is treated as retired. A live target with
an unsupported command remains `CDP_PROTOCOL_INVALID`. A detach observed while a
session command is pending becomes `CDP_TARGET_DETACHED` with its fixed phase and
target class. Raw target/session IDs and CDP error text are never logged.
